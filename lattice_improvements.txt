3. Wrapping the ranks of a versioning drawing onto several bands (`rank_wrap`), for bbv-anim and
   bbv-cfg, in both directions

   Summary. A versioning drawing (bbv-anim, bbv-cfg) puts every origin block of a function on a
   rank (a row with direction=TB, a column with direction=LR) and packs the versions of that block
   along the rank. A function with many ranks therefore gives a drawing much longer than wide (TB)
   or much wider than tall (LR), and since the drawing scales to fit its box, the node text shrinks
   until it cannot be read. This asks for an option that cuts the ranks of a function into
   consecutive groups, the bands, and lays the bands side by side (TB) or one under the other (LR),
   so that the drawing takes the shape of its box.

   How the layout works today (src/lattice/bbv/layout.py, Lattice 0.31). block_ranks gives each
   block a rank from a Graphviz layout of the source CFG. layout_frames places rank r of a function
   at a fixed offset along the "across" axis (y in TB, x in LR), the sum of the extents of ranks
   0..r-1 plus GAP_RANK (44 px) each, and centres the versions of the rank along the "along" axis
   within the function's extent, which is the widest rank over all frames. Functions sit side by
   side along the "along" axis, FUNCTION_GAP (64 px) apart. The drawing box is the union over all
   frames, and the runtime scales it to fit the component (up to 430 px high without `height=`).
   `wrap=` already wraps the versions of one rank onto several lines; nothing wraps the ranks.

   Test case A: a loop, SBBV, LR. The program, vector-print.bbv:

     function vprint(v)
     A:  goto L(i=0)
     L:  if vector?(v) goto B else goto K
     K:  fail
     B:  len = ##vector-length(v)
         if <(i, len) goto C else goto R
     R:  return #f
     C:  if vector?(v) goto I else goto F
     I:  if fixnum?(i) goto J else goto F
     J:  if fx>=(i, 0) goto N else goto F
     N:  len2 = ##vector-length(v)
         if fx<(i, len2) goto D else goto F
     F:  fail
     D:  e = ##vector-ref(v, i)
         t = display(e)
         if fixnum?(i) goto G else goto H
     G:  i2 = fx+?(i, 1)
         if i2 goto M else goto O
     M:  goto L(i=i2)
     O:  i3 = ##+(i, 1)
         goto L(i=i3)
     H:  if flonum?(i) goto W else goto X
     W:  i4 = fl+(i, 1.0)
         goto L(i=i4)
     X:  i5 = ##+(i, 1)
         goto L(i=i5)

   The block, in a column about 1050 px wide:

     ```bbv-anim {#vp program="vector-print.bbv" algorithm=sbbv heuristic=arithmetic limit=2 intervals=true vector_bounds=false direction=LR height=480}
     show: [label, context, code]
     thresholds: [0, 1, maxfix-1, maxfix]
     ```

   One function, 10 ranks, 74 frames. The drawing box is 2753 x 488 px (5.6 times wider than
   tall), so it is drawn at scale 0.38 and the 13 px code font shows at about 5 px.

   Test case B: recursion, Lambda Versioning, two functions. The program, fib-call.bbv (the
   classic fib with its operators expanded, called as (fib (read))):

     function main()
     M:  n = read()
         call fib(n) -> N
     N:  return #res

     function fib(n)
     A:  if fixnum?(n) goto B else goto C
     B:  if fx<=(n, 1) goto R else goto D
     C:  if ##<=(n, 1) goto R else goto D
     R:  return n
     D:  if fixnum?(n) goto E else goto F
     E:  n1 = fx-?(n, 1)
         if n1 goto H else goto I
     F:  if flonum?(n) goto G else goto I
     G:  n1 = fl-(n, 1.0)
         goto H
     I:  n1 = ##-(n, 1)
         goto H
     H:  call fib(n1) -> J
     J:  a = #res
         if fixnum?(n) goto K else goto L
     K:  n2 = fx-?(n, 2)
         if n2 goto P else goto Q
     L:  if flonum?(n) goto O else goto Q
     O:  n2 = fl-(n, 2.0)
         goto P
     Q:  n2 = ##-(n, 2)
         goto P
     P:  call fib(n2) -> S
     S:  b = #res
         if fixnum?(a) goto T else goto V
     T:  if fixnum?(b) goto U else goto V
     U:  r = fx+?(a, b)
         if r goto W else goto Z
     W:  return r
     V:  if flonum?(a) goto X else goto Z
     X:  if flonum?(b) goto Y else goto Z
     Y:  return fl+(a, b)
     Z:  return ##+(a, b)

   The block, at full slide width (about 1136 x 430 px of room):

     ```bbv-anim {#fib program="fib-call.bbv" algorithm=lv heuristic=arithmetic limit=3 entry=main direction=LR}
     show: [label, context, code]
     ```

   fib has 15 ranks, main 2; the run has 231 frames and ends with 56 versions. With direction=TB
   the box is 1850 x 2738 (scale 0.16, text about 2 px); with direction=LR it is 5116 x 1128 (scale

   rank, so its band is already tall, and stacking LR bands makes it taller still.

   So: wrapping is worth 40 to 60 % on case A and 35 % on case B; the best band count depends on
   the drawing and the box, and for B it is TB columns, not LR bands, that help. Case B stays small
   even then; that is a matter of node content and version count, not of this feature.

   Today: no option folds the ranks. `wrap=` only wraps versions within a rank, `direction` picks
   one of two shapes, `show:` narrows the nodes but leaves the rank count, `height=` cannot help
   when the width is the limit, and clicking a version to enlarge it is fine for a reader but not
   for an audience.

   Wanted syntax:

     ```bbv-anim {#vp ... direction=LR rank_wrap=2}
     ```
     ```bbv-anim {#fib ... direction=TB}
     rank_wraps: {fib: 2}          # per function, as limits: is to limit
     ```
     ```bbv-anim {#fib ... direction=TB rank_wrap=auto}
     ```

   - `rank_wrap` (integer >= 1, or `auto`; default 1, today's layout) applies to every drawn
     function; `rank_wraps: {FUNCTION: N | auto}` overrides it per function. Same options on
     bbv-cfg, so that a CFG following an animation can match its shape.
   - `rank_flow` (`restart`, the default, or `snake`): with `restart` every band reads in the same
     direction (left to right in LR, top to bottom in TB), like lines of text; with `snake` every
     second band runs backwards, which makes the edges between bands short at the cost of the
     reading direction.

   Layout rules:

   a. Cut. The ranks of a function, in rank order, are cut into N groups of consecutive ranks, so
      that the bands have about the same extent across (the sum of their rank extents, maximum over
      all frames). A rank is never split. N is clamped to the number of ranks.
   b. Static. The cut is computed once for the whole run, like the rank offsets today, so a version
      never changes band between frames and the runtime still only replays positions.
   c. Placement. In TB the bands of a function are columns side by side, left to right, each as
      wide as its widest rank; in LR they are bands one under the other, each as tall as its widest
      rank. The bands of one function stay together, with a gap between them smaller than
      FUNCTION_GAP (or the same gap plus a faint separator) so that they read as one function; the
      function's header sits above its first band. Functions keep their order (`functions:`).
   d. Edges inside a band are drawn as today.
   e. Forward edges between bands (from rank r in band i to a rank in band j > i): they leave the
      source on its usual side, run along a gutter outside the band (TB: below the last rank of
      band i, then across to the top of band j; LR: past the right end of band i, then down to the
      left end of band j) and enter the target on its usual side, without crossing nodes. With
      `snake` the gutter is the near end of the two bands. Edge labels (#t, #f, return indices)
      stay at the middle of the drawn curve, as today.
   f. Back edges: today they use a lane beside the function. With bands, a back edge within one
      band keeps a lane beside that band; a back edge from band j to an earlier band i runs in the
      gutters back to band i (in case A, the loop edges from M, O, W and X back to L: L is on
      rank 1, in the first band, while M, O, W and X are on the last rank). Several back edges keep
      nested lanes, as today.
   g. Call and return edges (ΛV) between functions are unchanged; they start and end at the nodes
      wherever their bands put them.
   h. `wrap=` still wraps versions within a rank, inside its band.
   i. `auto` picks the N (1 to the number of ranks, at most 6) that maximizes the scale. The build
      does not know the component's box (columns change width with `width` cues), so the build
      takes a target aspect: the `height` given (or 430 px) and the slide's content width, or an
      explicit `fit_aspect=W:H`. A stretch goal: lay out every N at build time and let the runtime
      pick by the measured box, changing only between steps, never while a step animates.

   Must keep working: arrows at versions and edges (`fib.A1`, `vp.L1->B1:true`), whose boxes come
   from the drawn nodes; the LT046 check of when a version is drawn; `paths:` frames (the path
   simply follows the edges through the gutters); a `bbv-cfg` following a `bbv-anim`; clicking a
   block to enlarge it; the panel and its placement; PDF export.

   Diagnostics: `rank_wrap` below 1 or not an integer or `auto` is an error; `rank_wrap` larger
   than the number of ranks is clamped with a warning; a `rank_wraps` key that is not a function of
   the program is an error.

   Acceptance: on case A with direction=LR rank_wrap=2 and on case B with direction=TB
   rank_wraps: {fib: 2}, the drawing box comes within about 10 % of the estimates above (1412 x 888
   and 2889 x 1438); no two nodes overlap in any frame; no edge between bands crosses a node; every
   version keeps its band across frames; and rank_wrap=1 reproduces today's positions exactly.

4. Paths through a Lambda Versioning run, from a program entry with no arguments, with the types
   returned by read() (slide "Example: polynomial and square", phd_these/src/lv.md)

   Need: once the ΛV run on programs/polynomial-square.bbv is done, highlight the path a flonum
   takes through the whole program, as `paths:` already does for SBBV. The program is

     function main()
     M:  x = read()
         call polynomial(x) -> N
     N:  return #res

   so the flonum is not a parameter: it comes from read(), whose result type is `any`.

   Today: `paths` is refused with `algorithm: lv` ("paths through calls are not defined"), even with a
   hand-written `versions:` list, because the check is on the algorithm (VersioningTrace._add_paths).
   Two more limits would remain once that check is lifted:
   - `input` must be a non-empty mapping over the parameters of the entry function, so a `main()`
     with no parameters cannot be given an input at all;
   - a path by `input` is read from the entry contexts on the parameters only; a variable computed
     on the way (here `x = read()`) is never narrowed (docs/todo.md, the 0.28.0 item on may-reach).
   The Lattice roadmap already lists "paths with algorithm: lv (through entry points, call edges and
   return points matched to their call sites)" in docs/todo.md; this request adds the read() part and
   the program entry, and gives a test case.

   Wanted syntax:

     ```bbv-anim {#ex-lv program="programs/polynomial-square.bbv" algorithm=lv heuristic=arithmetic limit=3 entry=main}
     show: [label, context, code]
     paths:
       - reads: [fl]                # the types returned by read(), in the order the calls execute
         caption: "(read) returns a flonum"
       - reads: [fx]
       - versions: [M1, A1, S1, V1, X1, B3, F1, G1, H1, N3]   # by hand, as for SBBV
     ```

   Requirements:

   a. Program entry with no arguments. A path starts at the entry version of the `entry=` function
      (the root of the run) and covers the whole program, all drawn functions. `input` becomes
      optional: an entry with only `reads`, or with `input: {}`, is valid for a function with no
      parameters. `input` and `reads` can be combined when the entry function has parameters and
      also calls read().

   b. `reads: [T1, T2, ...]`. The i-th read() executed along the path returns type Ti (any type
      that Type.parse accepts: fx, fl, bg, fx | bg, !fx, ...). The assignment `x = read()` then
      gives x that type, and the path keeps x narrowed from there on, through later versions and
      across calls (an argument passes its type to the callee's parameter). Once the list is
      exhausted, further read() calls return `any` (or an error, if the author prefers it strict:
      say `reads_exhausted: any|error`). Reads are counted in execution order along the path, so
      the walk has to carry a read cursor; in a loop the same read() can consume several entries.

   c. Calls and returns matched. Through a `call f[E](a) -> K` the path enters the entry version E
      of the call edge. At an exit site of f, the path returns to the return point of the same call
      site that carries the index of that exit (the return edges are labelled [0], [1], ...), not to
      every return point of K. This is call/return matching, so the walk keeps a call stack in its
      state; for recursion, cap the stack depth (or fall back to unmatched may-reach beyond the cap)
      and say so in the spec.

   d. Test of a version on the path: a version is entered when its entry context meets the types the
      path holds for its variables (parameters, read() results, #res after a return), as `admits`
      does today for parameters. A version whose context does not meet them is off the path, so for
      reads: [fl] the fixnum sides (T1, U1, W1, B1, B5, C1, ...) are left out.

   e. What is lit. Versions of the path get the `path` mark and the others `dim`, as for SBBV. Edges
      in state `path`: goto/#t/#f edges between path versions, the call edges taken, and only the
      return edges taken. When one return edge carries several indices (A1->B5 is [1] [3]),
      highlight the index used on its label if possible. A following `bbv-cfg` lights the blocks
      of the path in every function (meta "blocks" across functions).

   f. Caption. The automatic caption names the reads and the inputs (`(read) → fl`), lists the
      versions in order and counts the tests left on the path, as for SBBV.

   Expected result on this program (limit 3, heuristic arithmetic, entry main), for reads: [fl]:

     versions: M1, A1, S1, V1, X1, B3, F1, G1, H1, N3
     edges:    M1->A1 (call), A1->S1 (call), S1->V1 (#f), V1->X1 (#t),
               A1->B3 (return [2], the index of exit X1), B3->F1, F1->G1, G1->H1 (goto),
               M1->N3 (return [3], the index of exit H1)
     tests left: 2 (fixnum? in S1, flonum? in V1)

   That is: into square through its generic entry S1, out at its flonum exit X1, back into
   polynomial at its flonum return point B3, then out at H1 to main's flonum return point N3.
   For reads: [fx], the path should go through T1, both U1 and W1 (overflow is not decided by the
   type), B1 and B5, and the fixnum side of polynomial.

   Timeline: as for SBBV, path frames come after the `done` frame, so the slide reaches them with
   `ex-lv end-1`, `ex-lv end`. The slide currently ends with arrows on the final graph (the four exit
   sites of square, then A1->B1 and A1->B5); those would need `ex-lv ..end-N` once paths are added.

   Workaround meanwhile: none on the slide. A tour of arrows along the versions would show the order
   but would not dim the rest of the graph or light the call and return edges, so the deck waits for
   the feature.
