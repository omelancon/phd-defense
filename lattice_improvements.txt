Requests for the Lattice developers, from the defense deck.

1. A stepping Graphviz diagram (slide "Union of Incoming Contexts", src/background.md)

   Need: the interval lattice of thesis figure 2 beside the abstract interpretation, with nodes and
   edges highlighted step by step (operands of a union, its result, the widening edge).
   Today: `dot` is static, and `graph-anim` only draws circles laid out by Lattice (no boxes, no
   dashed or dotted edges, no "..." stubs, no ranks chosen by the author). The deck therefore ships a
   local plugin, `hasse-anim` (src/lattice_plugins.py, src/plugins/), that lays out a .dot file once
   and sets a state per node and edge per position.
   Wanted syntax, roughly what the plugin does:

     ```dot-anim {#lat file="figures/interval-lattice.dot" height=470}
     steps:
       - null
       - nodes: {s0: active, s1: active}
         caption: "{0} ∪ {1}"
       - nodes: {i01: done}
         edges: {s0->i01: path}
     ```

   with the theme states of graph-anim, deltas between steps, DOT `class="hidden"` for elements
   drawn only when a step names them, and its nodes and edges as arrow parts (`lat.mf1`,
   `lat.i02->mf1`), as the plugin already provides.

2. The panel of abstract-interp-anim at `panel_at: right` is capped at 40% of the width, so a
   widening chain such as `∇ [0, maxfix-1]` wraps inside its chip. An option for the panel width (or
   letting the history list take the room it needs) would allow the panel beside a narrow CFG.

3. Long SBBV runs in direction=LR become unreadable (slide "SBBV: Behavior with loops", src/sbbv.md)

   Need: vector-print.bbv has 13 ranks along the loop (L, B, C, I, J, N, D, G, M, ...), so with
   direction=LR the drawing is about 7 times wider than tall; at height=480 in a 5fr column it fills
   about a quarter of its box, and the node text is tiny. show: [label, context] barely helps, since
   the number of ranks, not the node width, sets the scale.
   Today: nothing folds the chain; wrap= only wraps versions within a rank.
   Wanted: an option that wraps the ranks of an LR drawing onto several bands (say `rank_wrap=7`:
   ranks 1..7 on a first band, 8..13 on a second, edges between bands routed down), or a layout that
   uses the height of the box when the drawing is much wider than tall.

4. Paths through a Lambda Versioning run, from a program entry with no arguments, with the types
   returned by read() (slide "Example: polynomial and square", phd_these/src/lv.md)

   Need: once the ΛV run on programs/polynomial-square.bbv is done, highlight the path a flonum
   takes through the whole program, as `paths:` already does for SBBV. The program is

     function main()
     M:  x = read()
         call polynomial(x) -> N
     N:  return #res

   so the flonum is not a parameter: it comes from read(), whose result type is `any`.

   Today: `paths` is refused with `algorithm: lv` ("paths through calls are not defined"), even with a
   hand-written `versions:` list, because the check is on the algorithm (VersioningTrace._add_paths).
   Two more limits would remain once that check is lifted:
   - `input` must be a non-empty mapping over the parameters of the entry function, so a `main()`
     with no parameters cannot be given an input at all;
   - a path by `input` is read from the entry contexts on the parameters only; a variable computed
     on the way (here `x = read()`) is never narrowed (docs/todo.md, the 0.28.0 item on may-reach).
   The Lattice roadmap already lists "paths with algorithm: lv (through entry points, call edges and
   return points matched to their call sites)" in docs/todo.md; this request adds the read() part and
   the program entry, and gives a test case.

   Wanted syntax:

     ```bbv-anim {#ex-lv program="programs/polynomial-square.bbv" algorithm=lv heuristic=arithmetic limit=3 entry=main}
     show: [label, context, code]
     paths:
       - reads: [fl]                # the types returned by read(), in the order the calls execute
         caption: "(read) returns a flonum"
       - reads: [fx]
       - versions: [M1, A1, S1, V1, X1, B3, F1, G1, H1, N3]   # by hand, as for SBBV
     ```

   Requirements:

   a. Program entry with no arguments. A path starts at the entry version of the `entry=` function
      (the root of the run) and covers the whole program, all drawn functions. `input` becomes
      optional: an entry with only `reads`, or with `input: {}`, is valid for a function with no
      parameters. `input` and `reads` can be combined when the entry function has parameters and
      also calls read().

   b. `reads: [T1, T2, ...]`. The i-th read() executed along the path returns type Ti (any type
      that Type.parse accepts: fx, fl, bg, fx | bg, !fx, ...). The assignment `x = read()` then
      gives x that type, and the path keeps x narrowed from there on, through later versions and
      across calls (an argument passes its type to the callee's parameter). Once the list is
      exhausted, further read() calls return `any` (or an error, if the author prefers it strict:
      say `reads_exhausted: any|error`). Reads are counted in execution order along the path, so
      the walk has to carry a read cursor; in a loop the same read() can consume several entries.

   c. Calls and returns matched. Through a `call f[E](a) -> K` the path enters the entry version E
      of the call edge. At an exit site of f, the path returns to the return point of the same call
      site that carries the index of that exit (the return edges are labelled [0], [1], ...), not to
      every return point of K. This is call/return matching, so the walk keeps a call stack in its
      state; for recursion, cap the stack depth (or fall back to unmatched may-reach beyond the cap)
      and say so in the spec.

   d. Test of a version on the path: a version is entered when its entry context meets the types the
      path holds for its variables (parameters, read() results, #res after a return), as `admits`
      does today for parameters. A version whose context does not meet them is off the path, so for
      reads: [fl] the fixnum sides (T1, U1, W1, B1, B5, C1, ...) are left out.

   e. What is lit. Versions of the path get the `path` mark and the others `dim`, as for SBBV. Edges
      in state `path`: goto/#t/#f edges between path versions, the call edges taken, and only the
      return edges taken. When one return edge carries several indices (A1->B5 is [1] [3]),
      highlight the index used on its label if possible. A following `bbv-cfg` lights the blocks
      of the path in every function (meta "blocks" across functions).

   f. Caption. The automatic caption names the reads and the inputs (`(read) → fl`), lists the
      versions in order and counts the tests left on the path, as for SBBV.

   Expected result on this program (limit 3, heuristic arithmetic, entry main), for reads: [fl]:

     versions: M1, A1, S1, V1, X1, B3, F1, G1, H1, N3
     edges:    M1->A1 (call), A1->S1 (call), S1->V1 (#f), V1->X1 (#t),
               A1->B3 (return [2], the index of exit X1), B3->F1, F1->G1, G1->H1 (goto),
               M1->N3 (return [3], the index of exit H1)
     tests left: 2 (fixnum? in S1, flonum? in V1)

   That is: into square through its generic entry S1, out at its flonum exit X1, back into
   polynomial at its flonum return point B3, then out at H1 to main's flonum return point N3.
   For reads: [fx], the path should go through T1, both U1 and W1 (overflow is not decided by the
   type), B1 and B5, and the fixnum side of polynomial.

   Timeline: as for SBBV, path frames come after the `done` frame, so the slide reaches them with
   `ex-lv end-1`, `ex-lv end`. The slide currently ends with arrows on the final graph (the four exit
   sites of square, then A1->B1 and A1->B5); those would need `ex-lv ..end-N` once paths are added.

   Workaround meanwhile: none on the slide. A tour of arrows along the versions would show the order
   but would not dim the rest of the graph or light the call and return edges, so the deck waits for
   the feature.
